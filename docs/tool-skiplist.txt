Evidence from a bounded feasibility scan (2026-07-22): (1) the actual jpegtran engine is `mozjpeg` 0.10 / `mozjpeg-sys` 2.2 — C FFI bindings that compile & statically link libjpeg-turbo via a C toolchain; like every C-library binding (pdfium-render, mupdf class) it will NOT instantiate under wafer's wasmi (needs libc/nasm/cc, pulls unavailable imports). (2) `lepton_jpeg` 0.5 (Microsoft's pure-Rust Lepton port) is the ONLY pure-Rust crate that truly parses baseline/progressive JPEG down to its quantized DCT coefficients, but its public API exposes ONLY whole-file `encode_lepton`/`decode_lepton` (+ `dump_jpeg`) — there is NO per-8x8-block coefficient read/transform/re-emit surface to hang a transpose on — AND it is fundamentally multithreaded (public `LeptonThreadPool`/`SimpleThreadPool` trait + `DEFAULT_THREAD_POOL` static, deps `thread-priority` + `cpu-time`), so even for the parts one could reach it falls in the same non-wasm-threading INSTANTIATE-gate class as the rayon/rawloader skips (no std::thread under the minimal WASI host / no wasm-threads on the browser build). (4) `mozjpeg-rs`/`oxideav-mjpeg` are pixel-domain encoders/codecs (decode→pixels / pixels→encode), not coefficient transformers. The only remaining path — decode→rotate→re-encode via the `image` crate — RE-COMPRESSES the JPEG (generational quality loss) and is therefore explicitly forbidden as it violates the tool's no-re-compression promise; it is also already exactly what blocks/rotate-image does (decodes to RGBA, rotates pixels, re-encodes). Revisit only if a proven wasm-safe, single-threaded pure-Rust crate that reads JPEG DCT coefficients, applies a jpegtran-style block transpose, and re-emits a valid JPEG lands, or if wasmi gains platform-wide wasm-threads and lepton_jpeg exposes a coefficient-transform surface. Scaffold not built.

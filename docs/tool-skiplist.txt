jpeg-lossless-rotate  # out-of-model / not viable: the row promises TRUE JPEG lossless rotation by DCT-block transposition with NO re-compression (jpegtran-style), which is a coefficient-domain operation — Huffman-decode the entropy stream to quantized 8x8 DCT blocks, transpose the block grid AND transpose/flip within each block, then re-Huffman-encode — never touching pixels. That requires libjpeg's coefficient API (jpeg_read_coefficients / jtransform_execute_transformation / jpeg_write_coefficients), and NO proven wasm-safe pure-Rust crate exposes it. Evidence from a bounded feasibility scan (2026-07-22): (1) the actual jpegtran engine is `mozjpeg` 0.10 / `mozjpeg-sys` 2.2 — C FFI bindings that compile & statically link libjpeg-turbo via a C toolchain; like every C-library binding (pdfium-render, mupdf class) it will NOT instantiate under wafer's wasmi (needs libc/nasm/cc, pulls unavailable imports). (2) `lepton_jpeg` 0.5 (Microsoft's pure-Rust Lepton port) is the ONLY pure-Rust crate that truly parses baseline/progressive JPEG down to its quantized DCT coefficients, but its public API exposes ONLY whole-file `encode_lepton`/`decode_lepton` (+ `dump_jpeg`) — there is NO per-8x8-block coefficient read/transform/re-emit surface to hang a transpose on — AND it is fundamentally multithreaded (public `LeptonThreadPool`/`SimpleThreadPool` trait + `DEFAULT_THREAD_POOL` static, deps `thread-priority` + `cpu-time`), so even for the parts one could reach it falls in the same non-wasm-threading INSTANTIATE-gate class as the rayon/rawloader skips (no std::thread under the minimal WASI host / no wasm-threads on the browser build). (3) `ljpeg` 0.1 and `pure_jpegli` 2.0 implement the PREDICTIVE lossless-JPEG *format* (ITU-T T.81 Annex H, DICOM Process 14) — a different codec entirely, not a baseline-DCT coefficient transpose; irrelevant to rotating ordinary lossy JPEGs. (4) `mozjpeg-rs`/`oxideav-mjpeg` are pixel-domain encoders/codecs (decode→pixels / pixels→encode), not coefficient transformers. The only remaining path — decode→rotate→re-encode via the `image` crate — RE-COMPRESSES the JPEG (generational quality loss) and is therefore explicitly forbidden as it violates the tool's no-re-compression promise; it is also already exactly what blocks/rotate-image does (decodes to RGBA, rotates pixels, re-encodes). Building this via `image` would ship a tool that LIES about being lossless. Revisit only if a proven wasm-safe, single-threaded pure-Rust crate that reads JPEG DCT coefficients, applies a jpegtran-style block transpose, and re-emits a valid JPEG lands, or if wasmi gains platform-wide wasm-threads and lepton_jpeg exposes a coefficient-transform surface. Scaffold not built.

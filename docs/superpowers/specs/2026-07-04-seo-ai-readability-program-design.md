# SEO & AI-agent readability program — design

Date: 2026-07-04
Status: approved scope ("do them all"), executing as a stacked PR train.

## Goal

Increase search-engine ranking potential and AI-agent/bot readability of
gizza.ai and its ~324 tool pages, building on the existing static-generator
foundation (per-tool pre-rendered HTML, llms.txt, sitemap, _index.json).

## Current state (audited 2026-07-04)

Strong baseline: every tool page is static HTML with title, meta description,
canonical, Open Graph, Twitter card, WebApplication JSON-LD, and an `index.md`
markdown twin. Site-wide: `sitemap.xml`, `robots.txt`, `llms.txt`,
`/tools/_index.json`, crawlable `/tools/` card grid. Generated by
`tools/generator` (Rust) + `scripts/gen-seo.sh`, deployed to Cloudflare Pages.

Verified gaps:

- **Cloudflare blocks AI crawlers at the edge.** GPTBot, ClaudeBot,
  PerplexityBot get HTTP 403; Cloudflare's managed robots.txt injects
  `Disallow: /` for ClaudeBot, GPTBot, CCBot, Google-Extended, Amazonbot,
  Applebot-Extended, Bytespider, meta-externalagent and signals
  `ai-train=no`. Our permissive robots.txt is appended after it. → Owner
  dashboard action (W0); all agent-readability work is invisible until fixed.
- One generic `og:image` (gis.png) for all pages; Twitter card is `summary`.
- No FAQPage/BreadcrumbList JSON-LD despite FAQ content existing in every
  `content.md` (`## FAQ` + `<details><summary>` blocks).
- `sitemap.xml` lacks `<lastmod>` (CI checkout is shallow — needs
  `fetch-depth: 0`).
- No related-tools links, no category hubs; homepage links only `/tools/`.
- Tool parameter JSON Schemas (`blocks/<slug>/manifest.json`) are not
  deployed; `_index.json` only has `{slug,title,description,tags}`.
- No `llms-full.txt`, no RSS/Atom feed, no IndexNow.
- No MCP server despite a full CLI (`gizza tool <slug>`).

## Workstreams

### W0 — Owner (dashboard) actions, not code

1. Cloudflare → AI Crawl Control / Bot settings: allow AI crawlers (at
   minimum ClaudeBot, GPTBot, PerplexityBot, Google-Extended for AI search
   visibility; `ai-train` signal is a policy choice). Disable or edit the
   managed robots.txt so the repo's file is authoritative.
2. Google Search Console + Bing Webmaster Tools: verify property, submit
   `https://gizza.ai/sitemap.xml`. Bing feeds ChatGPT search.
3. Re-verify with `curl -A "<bot UA>" https://gizza.ai/tools/` → expect 200.

### W1 — Structured data & metadata (PR 1, branch `seo/structured-data`)

- `template.rs`: BreadcrumbList JSON-LD (Home › Tools › {title}).
- FAQPage JSON-LD: generator parses `content.md`'s `## FAQ` section
  (`<details><summary>Q</summary>…</details>`), emits plain-text Q/A pairs;
  only when at least one FAQ exists. Unit-tested extraction (new `faq.rs`).
- Per-tool OG image `pkg/tools/<slug>/og.png` (1200×630), generated at build
  time in Rust (resvg/usvg/tiny-skia + bundled OFL font, new `og.rs`): brand
  mark, tool title, tagline. `og:image` → absolute URL,
  `og:image:width/height/alt`, `twitter:card=summary_large_image`.
  WebApplication JSON-LD gains `image`.
- `gen-seo.sh`: `<lastmod>` per URL from
  `git log -1 --format=%cI -- blocks/<slug>/page` (omit tag when git
  unavailable). `deploy.yml`: `fetch-depth: 0` on the gizza-ai checkout.

### W2 — Internal linking & architecture (PR 2, branch `seo/internal-linking`)

- New `categories.rs`: fixed category set (slug, title, blurb, match rules
  over tags/slug). Every tool lands in ≥1 category; unmatched → `utilities`.
  Build fails on category-slug collision with a block slug.
- Related tools: top 5 by shared-tag count (tie-break: same category, then
  slug order); rendered as a "Related tools" section on every page and in
  `index.md`.
- Category hub pages `/tools/<category>/`: h1, blurb, card grid, canonical,
  meta description, BreadcrumbList. Listed in sitemap via
  `pkg/tools/_hubs.json` consumed by `gen-seo.sh`.
- `/tools/` landing gains a category nav; homepage (`site/index.html`) gains
  a static "Popular tools" section (curated ~12) + category links.

### W3 — Agent surfaces (PR 3, branch `seo/agent-surfaces`)

- Emit `/tools/<slug>/tool.json`: `{slug, title, description, tags, category,
  urls: {page, markdown, deep_link_example}, cli, parameters}` where
  `parameters` is the JSON Schema from `blocks/<slug>/manifest.json`.
- Page `<head>` gains `<link rel="alternate" type="application/json"
  href="tool.json">`; the "Developer & Automation Access" section links it.
- `_index.json` entries gain `"schema": "/tools/<slug>/tool.json"`.
- `llms-full.txt`: header + concatenation of every tool's `index.md`
  (~1 MB); linked from `llms.txt`.

### W4 — Feeds & indexing plumbing (PR 4, branch `seo/feeds-indexnow`)

- Atom feed `/feed.xml`: newest 50 tools by first-commit date of
  `blocks/<slug>/page` (git); autodiscovery `<link>` on homepage + landing.
- IndexNow: committed key file `pkg`-deployed as `/<key>.txt`;
  `scripts/indexnow-ping.sh` submits URLs whose `blocks/<slug>/page/**` or
  `site/**` changed in the pushed range (cap 500) to `api.indexnow.org`;
  wired as a post-deploy step in `deploy.yml`.

### W5 — Format-pair landing pages (PR 5, branch `seo/format-pair-pages`)

- Nested under the converters to avoid slug collisions and keep topical
  clusters: `/tools/audio-convert/<src>-to-<tgt>/` and
  `/tools/image-convert/<src>-to-<tgt>/`.
- New `formats.rs` fact table per format (codec, container, lossy/lossless,
  strengths, typical use). Audio sources {mp3,wav,ogg,flac,m4a,aac,opus,
  aiff} × targets {mp3,wav,ogg,flac,m4a}; image sources {png,jpg,webp,gif,
  bmp,tiff} × targets {jpeg,png,webp}; identity pairs skipped (≈50 pages).
- Each page: unique title/description/h1, comparison table, why-convert
  prose assembled from the fact table (incl. lossy→lossless caveat), CTA
  deep-linking the parent tool with `?format=<tgt>` prefilled, breadcrumbs,
  2–3 pair-specific FAQs (+ FAQPage JSON-LD), `index.md` twin, sitemap
  entries; parent tool page links its pairs ("Popular conversions"), pairs
  cross-link siblings. Thin-content guard: every page carries ≥250 words of
  pair-specific prose derived from the fact table.

### W6 — MCP server (PR 6, branch `feat/gizza-mcp`, independent of the stack)

- `gizza mcp` subcommand: stdio MCP server (JSON-RPC 2.0: initialize,
  tools/list, tools/call) exposing every catalog tool with its manifest
  description + JSON Schema; tools/call runs the same execution path as
  `gizza tool <slug>`. Use the `rmcp` SDK if its pin is workable, else a
  minimal hand-rolled stdio loop. Documented in `cli/README.md`, `SKILL.md`,
  and llms.txt Resources.

## Sequencing & delivery

PR train: W1 → W2 → W3 → W4 → W5 stacked (each branch based on the previous;
GitHub retargets on merge). W6 branches from main in parallel. Every PR:
generator unit tests + full local generator run over the repo + shellcheck
for touched scripts; review-only (no self-merge). pkg/ stays gitignored —
all new artifacts are build-time outputs.

## Out of scope

- Paid link building / off-site SEO; hreflang & i18n; per-tool analytics.
- Server-side compute (remote MCP hosting) — the MCP server is local stdio.

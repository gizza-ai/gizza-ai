# payment-qr — competitor analysis (2026-08-06)

Scan run BEFORE implementation, per `/create-next-tool` step 3 (`/improve-tool` Phases 2–4).
All notes are **paraphrased observations of feature/UX behaviour** — no competitor copy,
branding, wording, or assets were reproduced or reused. The tool's own copy, FAQ, examples
and SVG layout are original.

Reference spec consulted alongside the competitors: BIP-0021 (bitcoin/bips), for the URI
grammar (`bitcoin:<address>[?amount=&label=&message=&req-*]`), the decimal-BTC amount rule
(period separator, commas invalid), and the "UTF-8 then percent-encode per RFC 3986" rule for
`label`/`message`.

## Competitors profiled

### 1. Spark — crypto QR generator (spark.money/tools/crypto-qr-generator)

- **Inputs:** chain dropdown (Bitcoin, Ethereum, Solana, Litecoin, USDC-ERC20, USDT-TRC20),
  address (required, with a paste affordance), amount (optional, units follow the chain),
  label/memo (optional, described as what the payer's wallet displays).
- **Schemes:** `bitcoin:` (BIP-21), `ethereum:` (EIP-681), `solana:`, `litecoin:`.
- **Validation:** prefix-shape only — Bitcoin must start `1`/`3`/`bc1`, Ethereum `0x`, Solana
  base58. Label/memo is URL-encoded automatically.
- **Output:** QR rendered through a remote chart image API; no stated file format, size, or
  error-correction control.
- **Positioning:** no sign-up, nothing stored, browser-local; 8 FAQ entries spanning BIP-21,
  amounts, wallet compatibility, merchant workflow, multi-chain.
- **Gap it exposes for us:** multi-scheme coverage is a genuine table stake, and so is a
  visible label/memo field. Its weakness: prefix-only validation accepts typo'd addresses, and
  the QR is generated by a third-party server (contradicting the browser-local claim).

### 2. QR Code AI — Bitcoin BIP21 generator (qrcode-ai.com)

- **Inputs:** address (legacy `1…`, P2SH `3…`, bech32 `bc1…`), optional BIP-21 `amount` in BTC
  and `label`.
- **Extras (paid/branding tier):** logo upload, brand colour, large template gallery,
  AI-generated designs.
- **Output:** PNG (screen), SVG (print), PDF (layered).
- **Validation / ECC:** neither documented on the page.
- **FAQ:** ~7 entries — creating the code, adding amounts via BIP-21, whether sharing an
  address is safe, Lightning invoice QRs, scanning, comparison with other payment QRs.
- **Gap it exposes for us:** colour customisation and an SVG-for-print output are expected;
  Lightning (`lightning:` BOLT11) is a question real users ask, so the scheme list should cover
  it rather than punting to the generic text path.

### 3. QRLynx — Bitcoin QR generator (qrlynx.com/bitcoin-qr-code)

- **Inputs:** one field — the receiving address. Explicitly states it only checks the field is
  non-empty and does **not** validate the address, its network, or ownership.
- **Payload:** address-only `bitcoin:<address>` — no amount, label, message, or Lightning.
- **Customisation:** colour/styling choices; guidance about contrast, quiet zone and print size.
- **Output:** static raster image; extra download formats gated behind an account plan.
- **FAQ:** ~11 entries — validation, adding an amount, Lightning, sharing safety, verifying a
  payment, testing before going live, whether an account is needed.
- **Gap it exposes for us:** honest limitations are worth stating on the page (a QR cannot
  prove address ownership, and no tool can confirm a payment arrived), but the *absence* of
  real validation is the single biggest weakness across all three — a mistyped address silently
  produces a scannable QR that sends funds nowhere recoverable.

## Diff vs what we built, and how each gap was resolved

| Gap seen in the scan | Fit | Decision |
| --- | --- | --- |
| Multiple chains, not just Bitcoin | in-model | Built: `scheme` enum — `bitcoin`, `litecoin`, `dogecoin`, `bitcoincash`, `ethereum`, `lightning`, `text`. |
| Amount / label / message BIP-21 params | in-model | Built as three separate params, percent-encoded per RFC 3986 (space → `%20`, never `+`). |
| Ethereum amounts | in-model | Built: EIP-681 `ethereum:0x…?value=<wei>` with exact decimal-ETH → wei conversion done in integer string math (no float rounding). |
| Lightning invoices | in-model | Built: `lightning:<bolt11>` with `lnbc/lntb/lnbcrt/lnsb` prefix + bech32-charset checking. |
| Real address validation (nobody does it) | in-model | **Built as our differentiator:** full Base58Check double-SHA-256 checksum + version-byte/network check, and full Bech32/Bech32m checksum + HRP + witness-version checking. A one-character typo is rejected with a specific reason. |
| Colour customisation | in-model | Built: `foreground`/`background` params using the generator's `kind = "color"` control. |
| Error-correction control | in-model | Built: `error_correction` enum L/M/Q/H, default M. |
| SVG output for print | in-model | Built: SVG is the native output (`format = "svg"` page + `image/svg+xml` envelope in chat/CLI), vector-crisp at any print size. |
| Explicit output size | in-model | Built: `size` in px (128–2048, default 512) driving the SVG viewport. |
| Human-readable URI printed under the code | in-model | Built: `show_uri` toggle, plus the URI always in the SVG `<title>` for screen readers. |
| PNG / PDF export | in-model, **rejected** | SVG downloads and converts losslessly, and the repo already ships `svg-to-png`; adding raster encoders here would duplicate an existing block for no gain. |
| Logo overlay in the QR centre | in-model, **rejected** | Needs a second image input, which this page shape has no surface for; `qr-styled` is the block that owns decorative QR rendering. |
| Template galleries / AI-generated designs | out of model | Not built — needs a hosted asset library and a model. |
| Accounts, plan-gated downloads, payment monitoring, dynamic/redirect QRs | out of model | Not built — all require a backend and an account; every gizza tool is browser-local and no-account. |
| Solana / USDC / USDT scheme entries | in-model, **rejected** | `solana:` (Solana Pay) and the token variants carry their own required params (`spl-token`, `reference`, chain-id-scoped contracts) that the BIP-21 grammar does not express; shipping them as bare BIP-21 URIs would emit URIs wallets reject. Listed here rather than faked.

## Honest limitations stated on the page

Carried over from the scan's better FAQ entries, in our own words: a QR code cannot prove who
owns an address, this tool cannot tell you whether a payment arrived, `amount` is a *request*
the payer's wallet can edit, and address validation checks the checksum/format only — it cannot
tell you the address is the one you meant.

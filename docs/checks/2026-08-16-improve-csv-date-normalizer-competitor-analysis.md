# csv-date-normalizer competitor analysis (2026-08-16)

## Scope

Tool: take a CSV whose date column holds more than one format (`2021-06-01`, `06/15/2021`, `15 Jan 2024`, `Tue, 15 Jan 2024 10:30:00 +0000`, the Excel serial `45000`, the Unix timestamp `1700000000`, and a row that just says `not a date`) and rewrite that column into one canonical format — ISO 8601 by default — resolving the `03/04/2024` day-first/month-first ambiguity from the column as a whole rather than cell by cell.

Research done 2026-08-16: a web sweep of the browser-local "standardize CSV dates" tools, plus direct reads of the documented parameter surfaces of the two libraries every one of those tools is modelled on (`pandas.to_datetime`, `dateutil.parser.parse`). Findings are paraphrased; no competitor copy, naming, or branding is reused.

## Competitor scan

| Source | Table-stakes found | In-model decision |
| --- | --- | --- |
| `pandas.to_datetime` (read the documented parameter table) | `dayfirst` / `yearfirst` hints for ambiguous 3-integer dates; `format` accepting an explicit strftime pattern, the literal `"ISO8601"`, or `"mixed"` to infer per element; `errors` = `raise` / `coerce` (bad values become `NaT`); `unit` for epoch input; `utc` to normalize offsets. The docs warn that `dayfirst` is **not strict** — pandas may ignore the hint when it can parse a string unambiguously another way — and that per-element `"mixed"` inference "is risky". | Built: `date_order` (`auto`/`day-first`/`month-first`), `on_error` (`keep`/`blank`/`error`), a `custom` format with a strftime `custom_format`, epoch + Excel-serial input recognised by magnitude, and `iso-utc`/`unix-*` output formats that resolve the offset. The documented risk is the thing we designed against: instead of per-element inference we do a **whole-column vote** and report `detected` / `default` / `conflict` as the reason, so the risky case is visible instead of silent. Also unlike pandas, an explicit `date_order` here IS strict for the values it applies to. |
| `dateutil.parser.parse` (read the documented signature) | `dayfirst` and `yearfirst` booleans (both default `False`), `fuzzy` parsing that pulls a date out of surrounding prose, a `default` date whose fields fill in whatever the string omits. | Built: day/month order as a tri-state including `auto`. **Considered, rejected: `fuzzy`** — extracting a date from arbitrary prose is exactly how a "notes" column silently becomes a date column; a CSV cell is either a date or it is not, and the unreadable-value report is the honest answer. **Considered, rejected: `default`/field-filling** — inventing an unstated day or month is a data-integrity hazard in a bulk rewrite; a partial value is reported as unreadable instead. `yearfirst` is unnecessary: a 4-digit leading component is already unambiguous, and this tool reads `2024-01-15` correctly with no flag. |
| Browser-local "standardize CSV dates" tools (search sweep: several independent free tools; one read directly) | The recurring shape: upload/paste a CSV, get every date as `YYYY-MM-DD`, run locally with no upload, leave unparseable values unchanged to avoid corrupting non-date data. The most capable of them advertises whole-dataset context for the MM/DD vs DD/MM decision (a value above 12 in the first position flips the column) and a 20+ format output list including RFC 2822, Unix epoch and SQL. The one fetched directly exposes **no** controls at all: one fixed output format, no column selection, no ambiguity override, no report. | Built: all of it, plus what they lack. Output is a 12-way list (four ISO variants, Unix s/ms, US, EU, SQL, compact, RFC 2822, custom strftime). Column selection is explicit (`columns` by header name or 0-based index) with `auto` as the default. The whole-column MM/DD vote is the core algorithm, and the `report`/`json` output modes expose the verdict, the counts, and the first 20 failures with row and line numbers — none of the scanned tools show their work. |
| Excel / Google Sheets round-trip (the source of the malformed data, and of two conventions the tool must honour) | The 1900 date system numbers days from 1900-01-01 with a phantom 1900-02-29, so serial↔date arithmetic is anchored at 1899-12-30; a fraction of a day is the time. Two-digit years pivot at 29/30 in Excel's own UI, while POSIX `strftime %y` pivots at 68/69. | Built: Excel 1900-system serials up to 2958465 (`9999-12-31`) with the fractional part as the time of day, behind an `excel_serial` toggle so a real numeric column can opt out; and a configurable `year_pivot` (0-99) defaulting to the POSIX 68, since the two ecosystems disagree and neither default is right for everyone. |

## Parameters and defaults

| Capability | Default / options | Status |
| --- | --- | --- |
| Ambiguous day/month resolution | `date_order` = `auto` (default; per-column vote from rows that can only be read one way), `day-first`, `month-first` | In model, built. The differentiator — and the reason `order_source` is reported. |
| Target output format | `format` = `iso-auto` (default, keeps each value's precision), `iso-date`, `iso-datetime`, `iso-utc`, `unix-seconds`, `unix-millis`, `us-date`, `eu-date`, `sql`, `compact`, `rfc2822`, `custom` | In model, built as `Param::enumv` → page `<select>` with worked-example labels. |
| Arbitrary output layout | `custom_format` strftime pattern, validated (`%Q` is rejected, not emitted literally) | In model, built. Matches pandas' `format=`. |
| Column selection | `columns` = `auto` (default), or header names / 0-based indexes, comma-separated | In model, built. `auto` requires ≥60% of non-blank cells to be *written* dates and never claims a bare-number column. |
| Unreadable-value policy | `on_error` = `keep` (default), `blank`, `error` | In model, built. Maps to pandas `errors=ignore/coerce/raise`. |
| Epoch input | Unix seconds and milliseconds, recognised by magnitude | In model, built; no `unit` parameter needed because the magnitudes do not overlap. |
| Excel serial input | `excel_serial` = on by default, 1 … 2958465, fraction = time of day | In model, built, with an off switch for genuinely numeric columns. |
| Two-digit-year century | `year_pivot` = 68 (POSIX default), range 0-99 | In model, built. |
| Header / delimiter handling | `has_header` = on by default; `delimiter` = `auto` (default), name, or single character; separator round-trips | In model, built. |
| Audit trail | `output` = `csv` (default), `report` (order + reason, per-column counts, first 20 failures with row and line), `json` | In model, built. No scanned competitor offers this. |
| Fuzzy / prose date extraction (`dateutil` `fuzzy=True`) | — | **Considered, rejected.** Pulling a date out of free text is how a notes column silently becomes a date column. Unreadable is reported, not guessed. |
| Filling in missing components from a `default` date (`dateutil` `default=`) | — | **Considered, rejected.** Inventing an unstated day or month during a bulk rewrite is silent data invention. `2021-06` is reported as unreadable instead. |
| Named time-zone abbreviations (`EST`, `CET`) and IANA zone conversion | — | **Considered, rejected for now.** `EST`/`CST`/`IST` are ambiguous across regions, and a real IANA database is a multi-megabyte dependency for a browser-local tool. Numeric offsets, `Z`, `UTC`, `GMT` and `UT` are accepted; anything else makes the value unreadable rather than silently mis-shifted, and the page says so. |
| Per-value locale/language month names beyond English | — | Out of model for this release: English full and abbreviated month names (plus weekday prefixes and ordinals) are supported. A multi-locale month table is a plausible future addition, not a table-stake in any scanned tool. |
| Repairing cell VALUES other than dates, type inference, row dedupe, header cleanup | — | Out of model; covered by the existing `csv-cleaner`, `csv-dedupe`, `csv-column-type-validator` and `csv-header-sanitizer` tools. Not built here. |
| Cloud batch jobs, saved profiles, accounts/API keys | — | Out of model: this repo's tools are browser-local, no-server, no-account. Not built. |

## UX decisions taken from the scan

- The day/month decision is the whole product, so it is surfaced three ways: a tri-state control, a per-column verdict in the report (`detected` / `default` / `conflict`), and an explicit warning line when a single column proves both orders. Competitors either hide the heuristic or have none.
- Default the tool to "auto-detect the column, auto-infer the order, ISO 8601 keeping precision, keep unreadable values" so the first render is already the answer for the majority case, and no default can destroy data.
- `format` and the policy params are `<select>`s with a worked example in every option label (`ISO date-time shifted to UTC — 2024-01-15T05:00:00Z`), because the difference between `iso-datetime`, `iso-utc` and `unix-seconds` is invisible from the name alone.
- Ship preset example chips for the recurring workflows: the mixed-format default pass, a forced day-first European pass, a serial/timestamp pass on a named column, an audit-report run, and a custom-pattern run.
- Auto-detection deliberately under-claims (never a bare-number column) and the page explains why in the FAQ, because the failure it prevents — a price column rewritten as dates — is unrecoverable, while the cost of under-claiming is typing a column name.
- State the limits on the page: the 5,000,000-byte cap, the 20-failures-per-column report cap, that impossible calendar dates are refused rather than rolled over, that unknown zone abbreviations make a value unreadable, and that the tool never reads the host clock or locale.
